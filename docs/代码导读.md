# 从一次修 bug 任务读懂 Agent Lab

## 先区分模型、harness 和环境

模型是一段策略：收到当前消息和工具说明，决定回复或请求工具。`ChatCompletionsModel` 把这些数据发给服务端，并拿回 JSON。

harness 是我们写的程序：`Agent` 循环、`Toolset` 工具、`RunStore` 日志、权限与停止条件。它不需要知道模型的内部结构。

环境是模型通过工具间接接触的东西：工作区文件，以及显式授权后的 bash 子进程。

## 第一层：主循环的六个动作

打开 `agent_lab/agent.py`，从 `Agent.run()` 开始。

1. 构造 `system` 和 `user` 两条消息。工作区和权限在本次运行中固定，不把不断变化的时间戳放入 system prompt。
2. 在调用模型前，计算消息加工具 schema 的字符长度。达到预算就明确停下，不调用模型。
3. 调用 `model.complete()`，记录输入、输出以及服务端提供的 usage。
4. 校验整批 `tool_calls`，再把原始 assistant 消息放进历史。
5. 有工具调用时逐个执行，并为每个 ID 添加一条 tool 消息，回到第 2 步。
6. 没有工具调用时，运行配置好的验证命令；通过则返回，失败则把证据加入历史继续。

`for step in range(...)` 是最终兜底：即使模型一直重复失败，或验证门永远不通过，也不会无限运行。

## 第二层：消息为什么必须这样排列

假设模型请求读取文件：

```json
{"role":"assistant","content":null,"tool_calls":[{"id":"a","type":"function","function":{"name":"read_file","arguments":"{\"path\":\"stats.py\"}"}}]}
```

这里 `arguments` 是一个 **JSON 字符串**。它和 Python 字典不一样，必须先 `json.loads`，并检查结构和类型。

执行后追加：

```json
{"role":"tool","tool_call_id":"a","content":"共 5 行；本页 1-5\n..."}
```

`tool_call_id` 指向发起请求的 `id`。有两个请求就要有两条回复；即使一个参数不合法，也要用带相同 ID 的错误回复告诉模型。不能漏掉 assistant 请求而只追加 tool 结果。

本实现先校验整批请求 ID。如果批次中有重复 ID，整轮不执行，避免先修改一个文件后才发现剩余请求的协议坏了。具体工具参数错误则成为可恢复的 `Error:` 观测。

## 第三层：工具说明也是模型输入

`tools.py` 中 `self.schemas` 描述了模型能调用什么。函数名称、description、parameters 都会进入每一轮请求。

例如 `edit_file` 的描述要求先读取、原文唯一匹配。实现中再次检查匹配次数：不能因为 prompt 里写了规则，就假设模型会遵守。

权限同样在代码中判断。系统提示只是告诉模型权限状态，真正阻止写入的是 `_require_write()`。工具集在本次运行中固定，不随着每一轮增删；这样历史中的工具名称始终有定义。

`read_file` 的行号用于定位，不属于文件内容。因此模型传给 `edit_file` 的 `old_str` 不应含 `12 | ` 这样的显示前缀。

## 第四层：控制观测量，保留找回信息的路径

如果命令返回长输出，`shorten()` 先将已捕获内容保存为 `output-0001.txt`，只把前缀、原长度、略去的字符数和 ID 发给模型。模型可以调用 `read_output` 取回中间某一段。

这和把旧历史删掉不同：旧消息不变，因此后一次模型输入仍以先前输入开头。具体有没有服务端缓存命中，还取决于服务商实现，不能从 append-only 直接推断费用节省。

注意两个不同上限：

- 捕获上限：bash 最多保留约 1 MB；超过部分没有落盘，无法恢复。
- 观测上限：进入模型上下文的单条结果默认约 6000 字符；落盘内容可以继续读取。

当前没有自动摘要。字符预算到了就停止，是可观察的限制；不会把“丢失历史后继续猜测”藏在黑箱里。

## 第五层：验证门为什么不问模型“通过了吗”

`--verify` 是用户配置的命令，程序直接判断退出码。模型说“完成”，但命令退出码非零，循环继续。离线演示还用单独的进程检查最终磁盘文件。

这只是机械检查，不等于独立 evaluator。模型能修改工作区里的测试，测试本身也可能覆盖不全。做严肃评估时，必须把验收规则和测试放在 Agent 无权修改的独立环境，或由人审查差异。当前实现没有把测试文件设为不可修改。

## 第六层：从日志理解失败

先看 `summary.json` 的 `status`，再在 `trace.jsonl` 中找最后一条事件。

| 状态 | 含义 | 下一步 |
| --- | --- | --- |
| `completed` | 模型正常结束；若配置验证门则已通过 | 查看文件差异和验证覆盖范围 |
| `max_steps` | 调用次数耗尽 | 检查是否反复报同一个错，或拆小任务 |
| `context_limit` | 输入字符预算耗尽 | 缩小读取范围，保存交接笔记后另开一次运行 |
| `model_error` | API、生成终止或响应协议异常 | 检查服务配置、模型工具调用支持及限流 |
| `runtime_error` | 本地执行或 I/O 异常 | 检查目录权限和运行环境 |
| `interrupted` | 用户按 Ctrl+C | 查看已落盘轨迹和文件差异 |

不自动恢复历史的原因是：恢复不仅是读 JSON，还需要验证模型、工具集、权限、工作区状态和未完成的工具往返。把这些约定做好后再扩展，比静默复用一段不匹配的旧状态容易理解。

## 可以自己动手的三个小实验

1. 让模型读取一个不存在的文件，看它是否能依据 `Error:` 调整路径。对比日志中的下一次参数。
2. 把 `--output-limit` 从 6000 调到 1000，观察 `read_output` 次数、总步数和实际 API usage 的变化。
3. 对同一个修 bug 任务，分别启用和关闭 `--verify`，用独立检查判断“模型声称完成”和“实际完成”的差异。

每次只改一个因素，用相同的初始工作区和任务。演示脚本用于验证代码路径；研究模型行为必须切换到真实模型。
